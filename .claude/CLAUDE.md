# Notes for Claude (and humans) - SchulyServer

ASP.NET Core 10 API. Clean architecture + CQRS via [Mediator](https://github.com/martinothamar/Mediator). EF Core on PostgreSQL. Built-in sign-in (Toamaisutaa). Plugin host.

## Workflow rules (enforced)

- Never work on `main`. Create an issue (labeled) → branch `feature/<issue#>_PascalCase`
  or `fix/<issue#>_PascalCase` → PR (labeled) with `Closes #<issue>` → squash-merge +
  delete branch.
- Use **bun** as the package manager / task runner - never npm, npx, or node directly.
- Use CLI tooling whenever one exists (`gh issue create`, `gh pr create`, generators, etc.).
- No AI / Claude attribution in commits or PRs. Ever.
- No test plans in PRs. PR body is **Summary** + `Closes #<issue>` only.
- Commit subject: short imperative.
- PR labels: `bug`, `enhancement`, `feature`, `refactor`, `CI/CD`, `dependencies`, `documentation`.

## Code formatting

Declaration signatures go on **one line** - never wrap the parameter list of a `record`, a primary-constructor `class`/`struct`, a method, or a constructor across multiple lines, however long it gets:

```csharp
// Yes
public record CreateAgendaEntryCommand(AgendaEntryType EntryType, string Title, string? Description, Guid? SchoolUserId) : ICommand<Result>;
public class GetSemesterReportsQueryHandler(SchulyDbContext dbContext, IUserService userService) : IQueryHandler<GetSemesterReportsQuery, Result<List<SemesterReportDto>>> { ... }

// No - parameter list wrapped across lines
public record CreateAgendaEntryCommand(
    AgendaEntryType EntryType,
    string Title,
    Guid? SchoolUserId) : ICommand<Result>;
```

**Keep wrapped as-is** (do *not* collapse): fluent / method-call chains (`.Where(...).Select(...)`), LINQ query expressions, and multi-line `if` / `while` / `for` / `switch` conditions and boolean expressions.

## Project layout

| Project | Role |
|---|---|
| `Schuly.API` | Entry point. Controllers, sign-in wiring (`/auth`), EF migrations applied on startup, plugin host registration. Has the `Dockerfile`. |
| `Schuly.Application` | CQRS commands/queries + Mediator handlers. **Don't** reference Infrastructure from here. |
| `Schuly.Domain` | Pure entities (`School`, `Class`, `Exam`, `Grade`, `Absence`, `AgendaEntry`, `ApplicationUser`, `SchoolUser`). Base type with `Id`, `CreatedAt`, `UpdatedAt`. |
| `Schuly.Infrastructure` | `SchulyDbContext` (incl. sign-in tables), user services, repositories, plugin runtime (`PluginBackgroundTaskHost`). |
| `Schuly.Sandbox` | Helply's sandbox sidecar (own image `ghcr.io/schulydev/schuly-sandbox`): microsandbox microVMs without network behind a keyed HTTP API. |
| `Schuly.Tests` | TUnit. |

`Schuly.Plugin.Abstractions` is a **NuGet `PackageReference`**, not a project ref - see the abstractions repo. Plugin projects live in a separate repo entirely.

## Adding an entity + endpoint

1. **Entity** in `Schuly.Domain` (inherits `Base`).
2. **DbSet + config** in `Infrastructure/SchulyDbContext.cs`.
3. **Migration**: `./scripts/migration.sh "AddXyz"` or `migration.ps1` on Windows.
4. **Command/Query** in `Schuly.Application/Commands/<Entity>/` or `Queries/<Entity>/`.
5. **Handler** alongside the command, registered automatically via Mediator source-gen.
6. **Controller** in `Schuly.API/Controllers/` - thin, delegates to Mediator.

## Migrations

```sh
./scripts/migration.sh "MigrationName"     # bash
./scripts/migration.ps1 "MigrationName"    # PowerShell
./scripts/DbScript.ps1                     # generate SQL script
```

Applied at startup by `ApplyMigrations()` in `Program.cs`.

## Auth

- Sign-in is built in via Toamaisutaa (`Toamaisutaa.*` 0.14.0). No external IdP. Tables live in the Schuly DB (migration `AddToamaisutaa`).
- Endpoints under `/auth` (register, login, refresh, logout, password, email, `2fa/*`, devices, `external/*` for optional OIDC single sign-on). `/api/*` takes `Authorization: Bearer`. Access tokens live 15 min; refresh tokens rotate on every use.
- Web app sends `X-Schuly-Client: web` and gets refresh + device tokens as `HttpOnly` `SameSite=Strict` cookies on `/auth`; other clients get them in the JSON body.
- Required secrets: `LocalLogin:SigningKey`, `TwoFactor:EncryptionKey` (base64, 32 bytes, keep stable). Set via user-secrets or env vars.
- There is no admin role. Every user is equal and only ever sees their own data; each personal-data query scopes to the caller's own `SchoolUser`s and answers 404 for anyone else's ids. School systems are seeded at startup and plugins come from `plugins.yml`; there is no runtime admin API.
- Locally, mail goes to an SMTP catcher on `localhost:1025` (e.g. mailpit). Get a token with `POST /auth/register` then `POST /auth/login`.
- Default policy requires auth; `/api/app` and the public `/auth` endpoints are anonymous.

## MCP server (`/mcp`)

- Official C# SDK (`ModelContextProtocol.AspNetCore`, pinned), Streamable HTTP, **stateless**. Tools live in `Schuly.API/Mcp/Tools`; host data goes through Mediator, plugin data through `InProcessPluginApi` (the app's own routing/authorization/plugin-scope pipeline, in process, with the caller's principal).
- Auth is our own OAuth 2.1 authorization server in `Schuly.Infrastructure/Mcp` (DCR, code + PKCE S256, rotating refresh tokens, opaque tokens hashed with SHA-256) plus user API keys (`schuly_mcp_...`). Both are accepted **only** by the `SchulyMcpToken` scheme on `/mcp`; `/api` JWTs are refused there and MCP tokens do nothing on `/api`.
- Every tool carries `[McpAccess(area, level)]` (and `[McpDestructive]` for deletes). Permissions live on the grant/key and are read on every request, so edits apply live. A new tool without `[McpAccess]` is visible to every connection: always add one.
- Consent page is the SPA route `/connect/authorize`; the decision API is `/api/mcp/*`. `Mcp:PublicUrl` and `Mcp:AllowedOrigins` (CORS + Origin check, no wildcard) are the only settings.
- Helply hooks: `McpInternalTokens` (short-lived token with its own permission set) and `Helply:BaseUrl`/`ApiKey`/`Model` from env only; never log or return them. Without `Helply:Model`, discovery probes the listed models with a tiny tool-call request and caches the first that answers.
- Helply's internal MCP call goes over loopback http with `Host` + `X-Forwarded-Proto` of the public URL; loopback is always a trusted proxy. Set `Mcp:PublicUrl` in deployments anyway.

## Helply files and workspace

- Attachments: `HelplyAttachmentStore` (Infrastructure). Type from magic bytes only (`HelplyFileTypes`), 20 MB, 5 per message, encrypted with the Helply cipher bound to user, conversation and `attachment:{id}:{part}`. Deleted with the conversation; unsent uploads after 24 h.
- The model gets attachments through markers in the session that `HelplyAttachmentExpander` expands on every request (`HelplyAttachmentStrategy`: native image/PDF, capped text, or a workspace pointer). Every tool call goes through `HelplyToolInvoker` (argument cap, repeat guard, result cap).
- Workspace tools (`bash`, `read_file`, `write_file`, `share_file`) exist only when the user enabled "Workspace" and `Helply:Sandbox:BaseUrl`/`ApiKey` are set. The workspace is wiped when the reply ends. Approvals that carry copied file content are flagged high risk (`HelplyLeakDetector`).
- microsandbox is beta and pinned (tag + digest) in `src/Schuly.Sandbox/Dockerfile`; change `Msb.CreateFlags` only with a real VM test. `--no-net` leaves only msb's own DNS answering (NXDOMAIN) on port 53.

## Versioning + release

Single source of truth: `application.properties`. `src/Directory.Build.props` reads via `XmlPeek`. Cutting a release triggers `docker-publish-release.yaml`:

1. `sync-version` job updates `application.properties` to match the tag via an auto-merged PR.
2. `build-and-push-sandbox` builds the sandbox sidecar (amd64) and pushes `ghcr.io/schulydev/schuly-sandbox` with the same tags.
3. `build-and-push-multiarch` builds the API container and pushes to:
   - `ghcr.io/schulydev/schuly:<semver>` (+ `:latest`, `:<major>`, `:<major>.<minor>`)
   - `<DOCKERHUB_USERNAME>/schuly:<semver>` (best-effort)

Docker build context is `./src` (Dockerfile's `COPY` paths are relative to it).
